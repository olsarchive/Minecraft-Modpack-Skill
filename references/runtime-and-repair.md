# 运行时证据与返修收敛

本指南来自实际返修；示例数量不是其它整合包的固定门槛。使用当前输入重新生成证据，不复用旧包 ID、哈希、目录或注册数量作为常量。

## 数据最终生效的四层

| 层次 | 要证明什么 | 仍不能证明什么 |
|---|---|---|
| 磁盘文件 | 结构可解析，引用和提供者集合闭合 | 实际被选中 |
| 资源栈 | 当前世界选中的包及顺序、同路径最终提供者 | 后续机制没有改写 |
| 最终解析对象 | 游戏内物种/任务/掉落的 ID、字段和引用 | 触发动作与玩家体验正常 |
| 实际行为 | 获取、使用、显示、效果、保存重进 | 全部变体与长期稳定性 |

### Cobblemon 掉落覆盖

先比较作者与本地有效 species；作者整份基础物种可能覆盖本地 Mega、骑乘、特殊形态等非 drops 字段。需要合并时以本地有效文档为底，仅添加已确认的新条目，保留所有原字段、掉落数量约束、条件和旧条目；以撤销新增后的结构等于原文档作为静态不变性检查。

然后查 `species_additions`、脚本与事件处理。装备、神兽或 DLC 的扩展可能在 species 加载后**再次替换整个 drops**。资源栈全部胜出仍可能丢硬币。记录每个扩展的 target、字段、来源和实际覆盖关系，必要时在同一兼容包中覆盖对应扩展文件，只追加所需条目。多来源同路径不一致时先确定真实赢家，不猜顺序。

真实案例中，576 个物种文件有 1718 条新硬币，修正资源栈后游戏内只有 1183 条；135 个物种受扩展覆盖。继续处理扩展后最终解析对象与作者 ID/percentage 全部吻合，并保留原非硬币掉落和形态。数字只用于说明为什么需要检查第二层覆盖。

全局加载器是否能在 `/reload` 时发现新 ZIP 要实际验证。本次环境需要完整重启才能发现新增全局包；已发现包的内容重载与发现新包是两件事。不要把改文件名为 `zz_` 当成优先级证明。

## 硬币、礼盒与外观链

按“注册物品→可获取来源→对应物种→佩戴/切换属性→resolver 条件/优先级→model/poser/texture→画面→保存重进”核对。礼盒 toggle 与原生 cosmetic 饰品可能是两套机制；命名空间不同不直接代表重复，也不代表可以安全卸载旧物品提供者。

- 佩戴成功、物品图标显示或属性存在，不等于皮肤已显示。选一个造型变化明确的款式作正对照，再检查普通/闪光、循环/替换、旧服装和本地 Mega 的相关组合。
- 光效、粒子与造型款分开观察。某个 Heaven 款没变不能立刻推出全部模型失效；也不能在没找到对应效果时擅自说“本来就是光效”。
- `getResource` 空而 `listResources` 有资源时，核对实际加载器使用哪条 API、namespace/path、前缀、供应者与选择顺序，再做实际渲染对照。曾观察到原生包按路径查询不一致，但批量加载的 April2024 造型及保存重进正常，因此没有修改 JAR。
- 模组自带加密/缓存资源时优先使用作者已有加载入口，不自制解密器、不把资源另行导出公开。读不到公开目录不等于缺模型。
- 某版原生玩法实际使用“手持硬币、Shift＋右键自己的宝可梦、给予饰品”，而非普通右键或给予携带物。操作方式以目标版本实测为准。

数千款内容做全量静态引用与重复检查，运行时按机制、提供者、变体抽样；只有对应样本可以标记已验证。掉落表 `percentage` 值不是每场战斗概率的实测证明；抽奖、兑换、云端服务分别验收，不能从本地注册成功推出线上服务可用。

## 临时诊断不要成为新的故障源

诊断放独立 TEST，默认只读。先用单物种/单资源确认脚本/API契约，再扩大集合；首次加载失败立即修诊断，不让用户反复启动去发现明显静态错误。临时探针报错单独归档，不归咎作者模组。

Rhino 不能按 Node.js 处理：Java 类过滤、重载、Map 访问和桥接包装可能与普通 Java 调用不同。曾发生禁止加载 ModList/StandardCharsets、Map 方法被当键、`get(1)` 误选 UUID 重载、字节数组选错构造器、循环中资源流重复关闭等问题。先使用加载器公开 API、无歧义迭代器和回调；作用域与关闭语义用一个小样本确认，不普遍宣称某个 JavaScript 关键字有问题。不能为探针关闭整个类过滤或添加广域异常吞噬。

需要桌面测试时绑定已观察到的目标实例窗口；输入后等待游戏响应并重新观察。鼠标侧键瞬时按下/松开可能未触发，短暂停留后验证再操作，不能在后台把输入发给其它应用。用户打断或禁止控制时停止桌面操作。没有可靠工具就保留未验证项，不用越权替代。

确认后移除临时探针，保存证据，再做一次不含探针的最终组合启动/世界验收；测试道具和命令不迁回 MAIN。

## 构建与负例返修

局部适配必须保持源码是输入，构建工具不能先删除/重建源码覆盖后续维护者修改。锁定源包、关键依赖、ID 清单和编译工具身份；记录构建命令、实际版本和目标哈希。相同输入重复构建应一致；不一致时先找时间戳/排序等原因，不能盲改预期哈希。

哈希不一致本身不是功能失败；先判断是否只有已解释的非功能元数据变化，再记录内容比较和复现限制，不能直接宣称功能失败或忽略差异。

产物先写临时位置，校验通过再替换正式产物，编译失败保留最后好包。负例只在临时副本中篡改，不能污染正式清单。组件契约检查要绑定到实际创建/赋值路径，不能在整份反汇编中搜索“出现过正确字符串”就通过。缺资源、缺 ID、错误 registry/namespace、依赖锁漂移和编译失败应有有意义的失败证据。

## 返修规则

记录触发动作→首个因果错误→假设→最小改动→对照结果→保留/撤回。条件无变化时不重复失败尝试；同一机制连续返修仍不收敛时先重新审核实现路径，优先找原生替代或恢复该链基线，不继续堆补丁。修掉首因后只把仍缺证据的链标记待测，不能把一次启动失败等同所有模块都失败。

任何组合改变，包括恢复旧 JAR 或隔离 DLC，都会使旧启动证据仅适用于旧组合。固定最终清单、重测后再应用，不能把“文件返修通过”写成“返修后的组合已启动”。
