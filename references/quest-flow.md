# FTB 老流程同步与 DLC 提供者核查

适用：新增章节已导入，但作者优化过的老章节仍可能沿用旧值；本地存在任务重编号、货币替换或旧进度。

## 以逻辑项审计，而不是只比较章节文件

对每个变化的任务记录以下字段：上游旧/新 ID、本地 ID、映射证据、条件及类型、前置、奖励、图标与文字、实际提供者、同步/保留/阻塞的理由及验证级别。没有共同基线时标为不明，不用文件日期代替祖先证据。

先稳定身份再同步逻辑：本地旧进度绑定的 ID 默认保留。使用章节位置、任务目标、前后置关系和条件内容共同确认语义对应，不能仅按翻译标题或同名章节自动认定等价。映射成立后将作者新前置转换成本地 ID，再检查全局依赖图。

分别统计与作者一致、仍是旧值、本地有意不同、缺提供者/需设计的项目；计数下降不是验收，必须能追到每一条决策。读取所有被更改章节的关联依赖，不局限于新增章节。

## 删除条件与删除奖励分开决策

- 作者删除旧手动或旧物品条件：确认当前目标机制及任务语义后同步删除，别因“保护旧档”把旧条件永远保留；也别为降低差异数直接清空条件。
- 作者新增自动判定：先证明精确提供者可用，再纳入。数值 `count: 1` 与字符串 `count: "1"` 不等价；SNBT 可解析不代表字段符合 FTB 契约。
- 作者删除奖励：任务完成、未领取、已领取是不同状态。先设计旧进度和未领取奖励的处理规则。证据不足时将奖励项独立暂缓，不重置整个任务、不执行奖励命令制造通过。
- 本地物品别名、货币、Mega 石及图标差异：确认对应的真实注册和经济语义后保留/映射，不为了逐字匹配上游换掉用户本地功能。

## “JAR 中没有”不是“没有提供者”

按实际加载配置检索活动 JAR、嵌套声明、全局 required/optional 数据包、资源目录被当作数据目录的入口、世界内数据包和有效 KubeJS 脚本。静态存在与实际启用分别记录；具体目录及文件夹单复数以当前 MC/加载器版本为准。

对挑战或冠军任务，核对任务条件→advancement/触发器→trainer→mob→loot/奖励的精确 ID 链，以及注册触发器的模组和对话/战斗桥接。DLC ZIP 可提供训练师与 advancement，不能只扫 `mods/*.jar`。反过来，四段 JSON 齐全也不证明桥接事件会触发，仍需要运行时战斗/对话验证。

确无精确物品或触发器提供者时标记阻塞，撤回已误装的条件；不要凭近似名字、新建空 advancement 或强发奖励补齐账面。

## 合并后验收

1. SNBT 往返解析、字段类型、重复 ID、本地身份映射。
2. 全局前置无悬空、无循环；保留的本地章节仍可达。悬空为零不证明流程正确。
3. 条件、命令、图标、奖励与所有实际提供者对照；任务背景所引用的资源必须可加载，不能仅检查 ZIP 文件存在。
4. TEST 用原玩家身份抽查关键新旧流程、完成触发和领奖，并保存重进。更改未领取奖励的测试只在副本进行，记录测试产生的状态。

若用户授权仅静态应用，结论写“证据闭合的静态流程已应用，完成/领奖未验证”；没有测试授权就不进入世界。
