# Runtime evidence and repair convergence

Use current inputs for evidence; example counts are illustrative, not universal thresholds.

## Four layers of runtime truth

| Layer | Proves | Does not prove |
|---|---|---|
| Disk files | Parsable structure and closed references/providers | Which provider wins |
| Resource stack | Selected packs, order, and effective provider | Later mechanics do not rewrite it |
| Parsed objects | In-game IDs, fields, and references | Player actions work |
| Behavior | Acquire, use, display, effect, save/reopen | Every variant or long-term stability |

Species files can overwrite local Mega, riding, or special-form fields. Merge from the effective local document and add only confirmed new drops, preserving all fields, quantities, conditions, and old entries. Then inspect `species_additions`, scripts, and events: they may replace the whole drops list later. Identify target, source, order, and actual winner; remove additions in a copy to prove the old structure is unchanged.

New global ZIPs may require a full restart to be discovered; reloading an already discovered pack is different. A `zz_` filename is not proof of priority.

## Coins, gift boxes, and cosmetics

Trace `registered item → acquisition → species → toggle/aspect → resolver priority → model/poser/texture → rendered result → save/reopen`. Gift-box toggles and native cosmetic accessories can be separate systems. A visible icon or successful equip does not prove rendering. Use a clearly different shape as a positive control, and test ordinary/shiny, cycling/default restoration, old clothes, and local Mega combinations. Separate shape changes from particles or glow.

If `getResource` is empty while bulk listing finds assets, check the loader's actual API, namespace/path prefixes, provider, and selection order before editing a JAR. Use the author's encrypted/cache loader; do not publish a custom decryptor or extracted restricted assets. Interaction such as “hold coin, Shift-right-click your own Pokémon, give cosmetic” is version-specific and must be confirmed in the target version.

For thousands of skins, statically check references and sample mechanisms/providers at runtime. A drop-table `percentage` is not an empirical battle probability; raffle, redemption, and online services are separate acceptance scopes.

## Diagnostics and build repairs

Keep probes in an isolated TEST. Confirm one species/resource and its API contract before scaling. Rhino differs from Node: class filters, overloads, Java Maps, UUID selection, byte-array constructors, and stream ownership need explicit unambiguous calls. Never disable the whole filter or swallow broad errors. Bind desktop input to the observed target window, wait for response, and stop when the user interrupts or forbids control.

Remove probes before the final clean run. Build from source without deleting or recreating it. Lock source archives, dependencies, IDs, JDK, command, and output hash; repeat builds and explain metadata-only differences instead of treating every hash change as a functional failure. Write artifacts to a temporary location, keep the last good build on failure, and mutate only temporary copies for negative tests. Contract checks must inspect actual creation/assignment paths, not a coincidental string in a decompile.

Record trigger → first causal error → hypothesis → smallest change → comparison → retain/withdraw. If conditions are unchanged, do not repeat the same failure. A changed combination, including restoring an old JAR or isolating DLC, invalidates earlier launch evidence; freeze the final manifest and retest it.
